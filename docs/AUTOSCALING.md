# Звіт з налаштування Автоматичного Масштабування (Autoscaling)

## 1. Параметри політики масштабування
- **Мінімальна кількість екземплярів (min_capacity):** 1
- **Максимальна кількість екземплярів (max_capacity):** 4
- **Цільова метрика:** Середнє завантаження процесора `ECSServiceAverageCPUUtilization` = **60%**
- **Scale-out cooldown (період стабілізації розширення):** 60 секунд
- **Scale-in cooldown (період стабілізації звуження):** 300 секунд

## 2. Обґрунтування цільового значення CPU (60%)
Поріг у 60% обрано для забезпечення балансу між економно використанням ресурсів та запасом міцності. Оскільки підняття нового контейнера Fargate зайняте певний час (викачування образу, ініціалізація), залишок у 40% CPU дозволяє існуючим екземплярам обробляти сплески навантаження без виникнення помилок 5xx до моменту введення в стрій нового контейнера.

## 3. Що таке період стабілізації (Cooldown) та дія при Cooldown = 0
**Cooldown (період стабілізації)** — це часова пауза після виконання дії масштабування, протягом якої система ігнорує нові сигнали на додавання або вилучення екземплярів, даючи метрикам час стабілізуватися.

- **Масштабування вгору (Scale-out = 60s):** Дозволяє новому контейнеру повністю стартувати та взяти на себе частину навантаження перед тим, як розраховувати середнє завантаження CPU повторно.
- **Масштабування вниз (Scale-in = 300s):** Запобігає передчасному вилученню контейнерів при короткочасних падіннях навантаження.

### Що станеться, якщо встановити Cooldown = 0?
Виникне ефект **Flapping (нестабільне коливання)**: система почне беззупинно створювати та видаляти контейнери. Наприклад, при перевищенні 60% CPU створиться новий контейнер, але поки він завантажується, метрика ще не встигне впасти — система негайно віддасть наказ створити ще один контейнер, досягнувши ліміту в 4 екземпляри. При падінні навантаження відбудеться аналогічне хаотичне видалення всіх екземплярів, що призведе до відмов у обслуговуванні (502/504 Bad Gateway).

## 4. Знімки панелі моніторингу CloudWatch
*(Сюди додаються скріншоти з CloudWatch Dashboard під час тесту)*
1. **Початок навантаження:** Наростання запитів.
2. **Перетин порогу CPU:** Перевищення позначки 60%.
3. **Поява нового екземпляра:** `DesiredTaskCount` та `RunningTaskCount` зростають з 1 до 2+.
4. **Вилучення екземпляра:** Зменшення кількості контейнерів після завершення тесту (з затримкою у 300 сек).
