# Звіт з налаштування Автоматичного Масштабування (Autoscaling)

## 1. Обрані параметри політики масштабування
- **Мінімальна кількість екземплярів (`min_capacity`):** 1
- **Максимальна кількість екземплярів (`max_capacity`):** 4
- **Цільова метрика:** `ECSServiceAverageCPUUtilization` = **60%**
- **Період стабілізації розширення (`scale-out cooldown`):** 60 секунд
- **Період стабілізації звуження (`scale-in cooldown`):** 300 секунд

## 2. Обґрунтування обраних параметрів
- **Цільове значення CPU (60%):** Позначку 60% обрано для забезпечення балансу між економним використанням ресурсів у звичайний час та наявністю 40% резерву потужності. Оскільки запуск нового контейнера у Fargate вимагає часу (викачування Docker-образу з ECR, ініціалізація таски), цей резерв дозволяє існуючим екземплярам обслуговувати сплески трафіку без помилок 5xx.
- **Scale-out cooldown (60с):** Забезпечує оперативну реакцію на зростання навантаження, даючи новому контейнеру 1 хвилину на запуск і стабілізацію перед наступною оцінкою.
- **Scale-in cooldown (300с):** Запобігає передчасному видаленню контейнерів при тимчасових паузах у трафіку, утримуючи резервні потужності протягом 5 хвилин.

## 3. Що таке період стабілізації (Cooldown) та ефект при Cooldown = 0
**Cooldown (період стабілізації)** — це затримка між операціями масштабування, протягом якої масштабувальний агент ігнорує нові тригери, очікуючи на оновлення метрик після зміни кількості екземплярів.

### Наслідки встановлення Cooldown = 0:
Виникає ефект **Flapping (нестабільне хаотичне коливання)**:
1. При перевищенні 60% CPU система віддасть наказ створити новий контейнер.
2. Оскільки cooldown відсутній, а новий контейнер ще не встиг підключитися і розвантажити процесор, при наступному вимірюванні CPU все ще буде >60%.
3. Система негайно створить ще один контейнер, швидко досягнувши ліміту `max_capacity = 4`.
4. Як тільки контейнери запуститься, середній CPU різко впаде — система миттєво почне їх видаляти.
5. Постійний перезапуск контейнерів призведе до падіння з'єднань, зростання помилок 502/504 Bad Gateway та зайвих витрат на Fargate.

## 4. Фіксація графіків на CloudWatch Dashboard (`cloud-lab1-dashboard`)
Під час навантажувального тестування k6 зафіксовано такі показники:
- **RequestCount (Кількість запитів за хвилину):** Пікове значення досягло **3.22K запитів/хв** (біля 09:00).
- **CPUUtilization (Завантаження CPU):** Піднялося від базлайну 0.28% до пікового значення **50.3%**.
- **Латентність p95:** Утримувалася на рівні **2.7 сек** під максимальним навантаженням.
- **Кількість екземплярів:** ECS Service підтримував роботу бажаного екземпляра в межах встановлених лімітів.
