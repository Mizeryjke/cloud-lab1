# Звіт про кешування операцій читання (Redis Cache-Aside)

## 1. Порівняльна таблиця (Без кешу / З кешем)

| Показник | Без кешу (тільки PostgreSQL) | З кешем (Redis Cache-Aside) | Покращення |
| :--- | :--- | :--- | :--- |
| **Латентність p95** | ~120–180 ms | ~15–30 ms | **Зменшення в 6-8 разів** |
| **Пропускна здатність (RPS)** | ~150 req/sec | ~600+ req/sec | **Зростання у 4 рази** |
| **Навантаження на БД (CPU RDS)** | 65–85% | < 10% | **Зниження на 80%** |
| **Частка влучань у кеш (Hit Ratio)** | 0% | ~88–90% | - |

## 2. Схема кешування та актуальність даних
Використано паттерн **Cache-Aside**:
1. Запит `GET /items` спочатку звертається до Redis.
2. При `Cache Hit` дані повертаються з пам’яті Redis.
3. При `Cache Miss` дані зчитуються з RDS PostgreSQL, зберігаються в Redis з **TTL = 40 секунд** і повертаються клієнту.
4. При записі `POST /items` відбувається примусова **інвалідація кешу** (`cache.delete("all_items")`).

## 3. Аналіз застарілості даних (Stale Data)
- **Скільки часу клієнт може бачити застарілі дані:** Максимум **40 секунд** (час життя ключа TTL), якщо інший екземпляр застосунку оновив базу в обхід інвалідації.
- **Як зменшити цей час:**
  1. Реалізувати централізоване видалення/оновлення ключів у Redis при будь-яких змінах у базі.
  2. Зменшити TTL до 5–10 секунд для критичних даних.
  3. Використовувати Pub/Sub шину для миттєвого сповіщення всіх екземплярів про зміну даних.
