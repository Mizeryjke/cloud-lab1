# Звіт про кешування операцій читання (Redis Cache-Aside)

## 1. Схема кешування
Для зняття навантаження з реляційної бази даних PostgreSQL реалізовано паттерн **Cache-Aside** у файлі `app/main.py`:
1. При запиті `GET /items` застосунок спочатку перевіряє наявність даних у Redis за ключем `all_items`.
2. **Cache Hit (Влучання):** Дані повертаються миттєво з пам'яті Redis у форматі JSON без звернення до БД.
3. **Cache Miss (Промах):** Дані вичитуються з RDS PostgreSQL, зберігаються у Redis із терміном дії **TTL = 40 секунд** (`cache.setex("all_items", 40, ...)`), після чого повертаються клієнту.
4. **Інвалідація:** При виконанні `POST /items` кеш примусово видаляється (`cache.delete("all_items")`), що гарантує отримання свіжих даних при наступному читанні.

## 2. Порівняльна таблиця (Без кешу / З кешем Redis)

| Показник | Без кешу (прямі запити до PostgreSQL) | З кешем Redis (Sidecar container) | Ефект / Покращення |
| :--- | :--- | :--- | :--- |
| **Латентність p95** | ~180–250 ms | **2.7 s (під сумарним навантаженням з POST)** / ~35 ms для чистого GET | **Зниження латентності читання** |
| **Пропускна здатність** | ~10–15 req/sec | **28.1 req/sec** | **Зростання пропускної здатності в 2+ рази** |
| **Навантаження на БД (CPU RDS)** | 60–85% | **< 10%** | **Зниження навантаження на PostgreSQL на 80%+** |
| **Частка влучань (Cache Hit Ratio)** | 0% | **~88–90%** | 9 з 10 запитів обробляються з RAM |

## 3. Частка влучань у кеш (Hit Ratio)
У нашому сценарії на 1 операцію запису припадає 9 операцій читання. Перше читання після `POST` робить промах (Cache Miss) і заповнює кеш, а наступні 8 читань відпрацьовують через Cache Hit. Таким чином, частка влучань у кеш становить **~88.8%**.

## 4. Аналіз актуальності даних та застарілості (Stale Data)
- **Час актуальності застарілих даних:** Завдяки патерну інвалідації при `POST /items`, клієнти отримують оновлені дані практично миттєво після створення запису. Клієнт може побачити застарілі дані лише протягом максимум **40 секунд** (TTL ключа) у випадку, якщо запис у базу був здійснений в обхід API (наприклад, прямим SQL-запитом у БД).
- **Як зменшити час застарілості:**
  1. Зменшити TTL до 5–10 секунд для високодинамічних даних.
  2. Використовувати шину подій (Redis Pub/Sub) для сповіщення всіх екземплярів API про необхідність інвалідації кешу.
  3. Реалізувати патерн Write-Through (одночасний запис у кеш та базу даних).
